# M3 讲解卡　食物、成长、分数、自撞判定

## 一、这一单元做了什么

场地里出现一个橙色圆点当食物。蛇头碰到它：长度加一、分数加一，食物换到新的随机空格子。
蛇头撞进自己的身体：游戏结束，蛇停在原地。另外还处理了两个边界：贴着尾巴走是合法的、场地被填满算通关。

**验收标准**：`mvn test` 全绿（共 21 个测试）；跑起来后吃到食物时，状态栏的"分数"和"长度"同时增加；
故意绕一圈咬到自己，画面显示"咬到自己了！"。

## 三、知识点 1：判定顺序不能乱

`advance()` 里的顺序是：**先看墙 → 再看自己 → 最后处理吃食物**。

如果先处理"吃到食物"，蛇会先变长，之后判断自撞时身体已经多了一节，
原本合法的走法可能被误判成撞到自己。所以代码先算出 `willEat`，
再用它参与判定，最后才真正移动和生长。

算法题里也常见这种"先把信息算齐再决策"的写法，比边走边改状态安全得多。

## 四、知识点 2：贴着尾巴走为什么不算撞

这是本单元最容易被写错的地方，很多业余实现都有这个 bug：

不吃食物的时候，尾巴会在这一步让开，所以**蛇头进入"尾巴当前所在的格子"是合法的**。
如果不做这个例外，玩家贴着尾巴走就会莫名其妙地死掉。

代码里就是这一行：

```
boolean followsTail = !willEat && nextHead.equals(snake.tail());
if (!followsTail && snake.occupies(nextHead)) { 判负 }
```

测试 `mayEnterTheTailCell` 专门钉住它：长度 6 的蛇向上、向左、向左、向下，
第十步正好进入尾巴格，断言"仍在进行中"。

## 五、知识点 3：随机位置有两种写法

**拒绝采样**：随便取一格，如果被蛇占了就重抽。蛇很长时可能连续抽中很多次，
极端情况下（比如蛇快占满场地）几乎抽不中。

**枚举法**（本项目采用）：先把所有空格列出来，再随机取一个下标。
最多扫一遍场地，40 × 28 = 1120 格，对计算机来说不值一提，而且行为稳定、必然成功。

结论：当"可用集合"可能很小的时候，不要用拒绝采样。

## 六、知识点 4：把随机性关进笼子

正式运行要随机，单元测试要确定。这两个要求是冲突的——怎么办？

把"食物放哪"抽成一个接口 `FoodSpawner`：

- 正式运行：`freeCells` 里随机取一个
- 测试：固定取蛇头右边那一格

这就是**依赖注入**的最小形态：把"会变化的部分"从类内部挪到构造参数上。
不抽出来的话，"吃到食物之后会发生什么"这类断言根本没法写——
食物每次落在不同地方，测试无法构造稳定场景。

## 七、知识点 5：那条"理论上不会发生"的路径

场地被蛇填满时，没有空格可以放食物。代码在这里让 `spawnFood()` 返回 `null`
并把状态置为 `WON`，绘制时也先判断 `food == null` 再画。

如果你不处理它，某天就会出现空指针。**处理一条边界比赌它不发生便宜得多**，
而且这几行顺便让"通关"变成了一个真实存在的状态。

## 九、动手改造点

1. 把 `spawnFood` 改成拒绝采样，再想一个能让它对蛇很长的局面明显变慢的测试。
2. 用完整构造器把初始长度设成 8：`new SnakeGame(40, 28, 8, 60, 8, spawner)`，
   开局就能手动试出咬自己。
3. 改规则：每吃 5 个食物额外加 2 分。改了规则就要同步改测试——体会"测试是规格说明书"。
4. 把食物的颜色和形状改掉，验证"绘制"和"逻辑"确实是分开的两层。
