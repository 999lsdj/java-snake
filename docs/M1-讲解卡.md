# M1 讲解卡　窗口 + 固定步长游戏循环

## 一、这一单元做了什么

打开一个 800×600 的窗口，里面画网格和状态文字；后台有一条循环线程，稳定地以每秒 60 次的节奏
驱动逻辑更新和界面重绘。窗口上实时显示实测帧率、累计更新次数和最近按下的键。

**验收标准**：`mvn clean package` 全绿；`java -jar target/java-snake-0.1.0.jar` 能打开窗口；
窗口里的实测帧率在 58~61 之间波动，不会掉到 30 以下，也不会冲到几百。

## 二、为什么要有游戏循环

游戏和普通程序最大的区别是：它**一直在变**。没人按键盘的时候蛇也要往前走，画面也要刷新。
所以游戏程序的心脏是一个永不停止的循环：更新逻辑 → 画出来 → 等一下 → 再来一遍。

## 三、核心知识点：固定步长

### 错误做法

```java
while (true) {
    update();   // 逻辑更新
    repaint();  // 重绘
    Thread.sleep(16);   // 想睡 16 毫秒 ≈ 60fps
}
```

问题在于 `Thread.sleep(16)` 只保证"至少睡 16 毫秒"。系统忙的时候它可能睡 30 毫秒，
那么这一帧游戏世界就前进了 30 毫秒的距离——蛇的速度会随电脑负载忽快忽慢。
同样的代码，在你的电脑上和评测老师的电脑上跑出来的手感不一样，这是不能接受的。

### 正确做法

把两件事分开：

1. **真实流逝的时间**：用 `System.nanoTime()` 量出来，是准确的；
2. **逻辑推进的步数**：永远按 1/60 秒一步走，与真实时间无关。

于是循环变成"时间攒够一步就更新一步"。如果某一帧卡了 50 毫秒，那就连续补跑 3 次逻辑更新，
让游戏世界追上来。这就是 `GameLoop.runLoop()` 里那段内层 while 的作用：

```java
while (accumulated >= stepNanos) {
    update.run();          // 逻辑更新一次
    updateCount++;
    accumulated -= stepNanos;
}
```

`accumulated` 是"攒下来的时间"。它像一个水桶：每帧往里倒水，水够一个步长就舀出去一勺，
舀几次取决于这一帧倒进去多少水。桶里剩下的水留到下一帧用，所以长期来看逻辑节奏是精确的。

## 四、第二个知识点：为什么要抽接口

`GameLoop` 的构造器可以接收 `nanoTime` 和 `sleeper` 两个参数。为什么给一个游戏循环
留这种"后门"？看测试就明白了：

```java
private static final class VirtualClock implements GameLoop.Sleeper {
    private final AtomicLong now = new AtomicLong();
    @Override public void sleep(long nanos) { now.addAndGet(nanos); }   // 不睡，直接推时间
}
```

假时钟的 `sleep` 不真的等待，只是把"当前时间"往后挪。于是测试可以在几毫秒内模拟出 1 秒的
游戏时间，跑到第 60 次更新后断言循环停下。如果时钟写死在代码里（直接调 `System.nanoTime()`
和 `Thread.sleep`），这个测试就只能真的等 1 秒，而且没法精确断言跑了多少次。

**这条经验会反复出现**：代码里凡是"看现在几点""睡一会儿""读文件""发网络请求"这类和外部世界
打交道的地方，都值得抽成接口。抽出来之后，最难测的部分就变成了最容易测的部分。

## 五、第三个知识点：Swing 的线程规则

Swing 有条铁律：**所有对界面组件的操作都在事件分发线程（EDT）上执行**。

- 创建窗口、`setVisible`、`add`、`setText` —— 都在 EDT 上做（所以 `Main` 里用 `SwingUtilities.invokeAndWait`）；
- `repaint()` 是唯一的例外，它被设计成线程安全的，所以游戏线程可以直接调用；
- `paintComponent` 一定在 EDT 上执行，所以 `GamePanel` 里的 `fps`、`lastKey` 这些字段
  **不需要**加锁——但 `ticks` 是游戏线程写的、EDT 读的，就必须标 `volatile`。

判断要不要 `volatile`，只需要问一句：这个字段有没有被两条以上的线程碰？

## 六、代码怎么读

建议按这个顺序读，一共不到 200 行：

1. `GameConfig` —— 先看常量，知道窗口多大、帧率多少；
2. `Main` —— 看程序怎么启动：先建窗口，再起循环；
3. `GameLoop.runLoop()` —— 整个单元的核心，配合本文第三节读；
4. `GamePanel.paintComponent` —— 界面是怎么画出来的；
5. `GameLoopTest` —— 看测试怎么用假时钟验证循环。

## 七、动手改造点

这些改造都不影响正常功能，改完再跑一遍，观察窗口上数字的变化：

1. 把 `GameConfig.TARGET_FPS` 改成 10，再改成 240，看"实测帧率"和画面刷新有什么变化；
2. 把 `GameConfig.TILE_SIZE` 改成 25 —— 会在启动时直接抛异常。这是 `GameConfig` 里的断言
   在起作用（800 除不尽 25），想一想为什么当初要加这条检查；
3. 在 `GameLoop` 里把内层的 `while` 改成 `if`，再用一个耗时的操作（比如 `Thread.sleep(100)`
   放进 `updateGame`）制造卡顿，观察游戏节奏是否还能追上真实时间。
