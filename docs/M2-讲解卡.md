# M2 讲解卡　蛇的移动、键盘控制、撞墙判定

## 一、这一单元做了什么

蛇出现在场地中央，用方向键能控制它转向，每秒走 8 格；蛇身按"头进尾出"移动；撞到墙就停住并弹出提示。

**验收标准**：`mvn test` 全绿（共 17 个测试）；运行起来后用方向键能让蛇拐弯；一直往一个方向走，撞墙后画面出现"撞到墙了！"。

## 三、知识点 1：为什么蛇身用 ArrayDeque

蛇每走一格只做两件事：**在头部加一格、在尾部删一格**。

- `ArrayDeque`（双端队列）：两端增删都是 O(1)
- `ArrayList`：尾部删是 O(1)，但**头部插是 O(n)**——要把后面所有元素整体后移

蛇长 100 格、每秒走 8 步时，用 ArrayList 每秒要搬运 800 个元素，完全是白干的活。
这就是"选对数据结构"的实际意义，比背概念有说服力。

顺带回答一个面试常问的比较：`LinkedList` 两端操作也是 O(1)，但每个节点是独立对象、
内存分散，`ArrayDeque` 用一块连续数组实现，实际跑起来更快、更省内存。所以 Java 官方也推荐
用 `ArrayDeque` 而不是 `LinkedList` 当栈和队列。

## 四、知识点 2：record 带来的 equals 和 hashCode

`GridPoint` 写成 `public record GridPoint(int col, int row)`，编译器自动生成构造器、访问器、
`equals`、`hashCode`、`toString`。

**关键在 equals**。`Snake.occupies()` 内部调用 `List.contains()`，而 `contains` 用的是 `equals`。
如果用普通类而忘了重写 `equals`，比较的就变成"是不是同一个对象引用"，结果永远为 false——
表现是"蛇明明占了这一格却判断不出来"，这种 bug 非常难查。

record 让这类错误从"容易犯"变成"不会犯"。这也顺便为 M5 的优化铺路：
将来把蛇身换进 `HashSet` 查重时，`hashCode` 是必需的，而 record 已经给了。

## 五、知识点 3：把方向写成数据，而不是 if/switch

每个方向自带位移量 `(dx, dy)`，屏幕坐标 y 轴朝下，所以"上"是 `(0, -1)`。于是：

- 走一格 = `col + dx`、`row + dy`，一行代码
- 判断反向 = 位移量相加的两个分量都是 0

如果换成四个 if 判断，那么"走一格""判断反向""计算新位置"每处都要重复写四遍方向逻辑，
以后加方向（比如斜向）就得改所有地方。**把变化写进数据，逻辑就只有一份。**

## 六、知识点 4：速度 ≠ 帧率

游戏循环每秒跑 60 帧，但蛇每秒只走 8 格。两者必须分开，否则蛇会以每帧一格的速度飞出去。

做法是"蓄水计数器"：

```
每帧：       accumulator += movesPerSecond
当 accumulator >= ticksPerSecond 时：
             accumulator -= ticksPerSecond
             蛇走一格
```

算一下：8 格/秒、60 帧/秒，平均每 7.5 帧走一格。**注意不是"每 7 帧走一格"**——
60 除以 8 除不尽，取整会累积误差：按每 7 帧一格算，实际是每秒 8.57 格，一分钟就快了 34 格。
蓄水计数器的余数会留到下一帧，长期平均速度精确。

这跟 M1 里那个 `accumulated` 是同一个算法，只是单位从纳秒换成了帧数。**M1 的固定步长，到了 M2 就直接变成速度控制的基础。**

## 七、知识点 5：输入缓冲与反向过滤

**问题**：如果只记录"最近按下的方向"，玩家在两格之间快速按了 ↑ 再按 ←，第一次会被第二次覆盖掉，
蛇看起来"漏掉了一次转向"。

**解法**：用一个队列，最多排两次转向，每次移动前只取队首的一次。

**反向过滤要做两次**，这里最容易写错：

1. 加入队列时，以"最后一次**已计划**的转向"为基准判断，而不是以当前方向为基准。
   如果以当前方向为基准：向右走时先按 ↑（合法，入队），再按 ↓（相对"当前方向右"也合法，入队），
   队列里就排了 ↑ 和 ↓ 两个互相反向的转向。
2. 真正应用时再过滤一次，把这种情况的第二次丢弃。

代码里两处都做了判断，是刻意的双保险。
